# Metic — 3D Art Spec

> **Status:** Adopted (2026-09-24): kit, build script and `ship_player` exist. Owner: whoever touches `art/`. Update this file
> and the AGENTS.md Decision Log when a rule here changes.

How Metic's 3D models (player ships, space monsters, props) are designed and
produced. The key constraint: models are **generated by Python scripts run in
Blender**, written mostly by an AI agent, so the style is chosen to be cheap to
author (few tokens per model) while still looking good in a phone browser.

---

## 1. Constraints from the game

- **Top-down camera.** The playfield is seen from above with a narrow-FOV
  perspective (see AGENTS.md → 3D rendering). Models are read mostly **from the
  top**; sides show only while aliens sway and the ship banks.
- **Small on screen.** An alien is ~24–56 px wide on a 480×720 field, and a phone
  shrinks that further. **Silhouette and 2–3 big color areas beat detail.**
- **The math is the star.** The numbered balls must stay the most readable thing
  on screen. Monsters must never compete with them (see §4).
- **Mobile browser budget.** Small downloads, few draw calls, no heavy shaders.
- **Multiplayer future (Tetris 99-style).** We will need many cheap variants:
  per-player ship colors, "attack" aliens sent by opponents, etc.

## 2. Style decision: why low-poly

| Style | Tokens per model (agent) | Look | Verdict |
| --- | --- | --- | --- |
| Voxels auto-built from existing sprites (current) | ~0 | Retro, consistent | Keep as fallback; limited to the 13 existing aliens + ship |
| Hand-authored voxel grids | High (a 16×16×8 grid is ~2k cells of data) | Retro | No |
| **Chunky low-poly, flat-shaded, palette colors, built by scripts** | **Low** (~40–80 lines per model on top of a shared kit) | Toy-like, clean, modern | **Chosen** |
| Smooth/sculpted organic + painted or PBR textures | Very high; not feasible without a human artist | Realistic | No |
| Geometry generated directly in Three.js code | Lowest | Same as low-poly | Possible, but not editable in Blender; keep for simple effects only |

Why low-poly suits an agent: a model is a short **recipe** of a few primitives
(convex hulls from ~10 points, tubes, blobs, skin-modifier skeletons). Colors come
from one shared palette, so there are no textures to paint. Flat shading hides
low triangle counts and turns them into a deliberate style.
**Proof:** the first test built a ship (166 tris) and a monster (648 tris) from
~100 lines of Python and ran in ~6 s headless.

## 3. Style pillars

1. **Readable from the top.** Features that matter (cockpit, eyes, mouth, glowing
   parts) face **up (+Z in Blender)**, toward the camera.
2. **Chunky and toy-like.** Big simple masses, exaggerated proportions (monsters:
   big eyes/head, stubby or tentacle limbs; ships: fat hull, clear wings).
3. **Flat shading, hard facets.** No smooth normals, no bevels.
4. **Few colors per model.** One base color + one shade + one accent + (optional)
   one emissive glow. Colors come only from the palette.
5. **Glow = gameplay meaning.** Emissive is reserved for engines, eyes, weak
   points, and bonus/attack markers, never decoration.

## 4. Palette

One palette texture (a strip of N×1 px swatches) shared by every model. Faces
pick a swatch by UV, so **one material + one tiny texture covers everything**, and
recoloring a model = swapping the palette (free skins).

Reserved hues. **Monsters must not use these as their main body color:**

| Reserved for | Hex | Why |
| --- | --- | --- |
| Number balls: sum | `#4EA1FF`-ish blue | Ball color = math operation |
| Number balls: subtraction | red | 〃 |
| Number balls: multiplication | green | 〃 |
| Number balls: division | yellow | 〃 |
| UI accent | `#4EA1FF`, `#FFD166` | HUD already uses these |

Monster body hues: purples, magentas, teals, oranges, pinks, greys. Player ship:
cool lavender/steel with a per-player accent color in multiplayer.
The swatch list will live in `art/palette/palette.json` (name → hex). Adding a
swatch is fine; renaming one breaks recipes.

> Note: the style test used a green monster only for illustration. Final monsters
> follow the table above so green balls stay unambiguous.

## 5. Geometry, scale & axes

- **Units:** 1 Blender unit = 1 game px (logical 480×720 space). Model at final
  size; the game does not rescale per model.
- **Size classes:** player ship ~32–40 wide · small alien ~24–32 · large alien
  ~40–56 · boss (future) ≤ 120.
- **Axes (Blender):** forward/nose = **+Y**, top (faces the camera) = **+Z**,
  origin = visual center of the body.
- **Aliens face -Y** (face/mouth/fangs toward the player, since they descend)
  and put `socket_balls` above the body at +Y, far enough out that the 9 px
  balls don't hide the face (darter +28, drifter +26, lumberer +30,
  strafer +30). Game logic keeps a copy of each offset (`MONSTERS[kind].BALLS_Y`,
  plus `HALF_W`/`BOTTOM`) for its readability box: **update them together** when
  a monster's size or socket changes.
- **Export:** glTF binary (`.glb`), `export_yup=True`, modifiers applied. The
  runtime loader rotates each model `rotation.x = +π/2` so Blender +Y → screen up
  and Blender +Z → toward the camera. *Verify once with an asymmetric test model.*
- **Triangle budgets:** ship ≤ 600 · alien ≤ 900 · boss ≤ 2,500 · prop ≤ 200.
- **File size:** ≤ 60 KB per `.glb` (meshopt/Draco compression optional later).
- **Materials:** only `M_Palette_lit` (matte) and `M_Palette_glow` (same palette
  as emission). Nothing else.
- **No interior faces**; parts may overlap (it's a toy), but never duplicate a face.

## 6. Sockets and animation (no rigs)

Skeletal rigs are expensive to author by script and heavy to run on phones, so
models animate as **rigid named parts** driven by game code:

- Static parts are **joined** into one mesh (one draw call).
- Moving parts stay **separate child objects** named `anim_<role>[_L|_R|_<n>]`,
  e.g. `anim_tentacle_L_1`, `anim_eye_R`, `anim_antenna_L`, `anim_flame_L`.
  The game wiggles, blinks, or scales them procedurally (sine waves, squash).
- **Sockets** are empties the game reads for positions:
  `socket_balls` (where the number-ball row sits, aliens only),
  `socket_muzzle` (bullet spawn, ship), `socket_engine_L/R` (trail/flame FX).

## 7. Number balls

Balls are **glass spheres with the number floating inside**
(`src/render3d/NumberBall.ts`), built in game code, not in Blender:

- A smooth sphere (the one exception to flat shading) with a cheap custom glass
  shader: tinted by the operation color, clearer in the middle so the digit
  reads, bright at the rim, one baked highlight. It ignores scene lights, so
  balls read the same everywhere and cost almost nothing on phones.
- The digit is a camera-facing plane textured from a canvas (bold monospace,
  white with a dark outline), never modeled geometry.
- Balls do not rotate. Radius `RENDER3D.BALL_RADIUS` (9 px), row spacing
  `ENEMY.BALL_SPACING` (20 px). Color = operation (`RENDER3D.BALL_TINT`, §4).

### Ideas to iterate on (not decided)

The balls are also a design space for monsters. Candidates to prototype:

- **Eyelid balls:** a sphere opens and closes like an eye; the number is only
  readable while it's open (timing pressure, a "blinking" monster).
- **Monsters made of balls:** the body itself is a cluster of number spheres
  (caterpillar, molecule, grape bunch) instead of balls floating above a body.
- Whatever we try, the number must stay the most readable element on screen.

Each ball is its own `THREE.Group`, so lids, shells or links can be attached
without changing callers.

## 8. Pipeline (all inside this repo)

```
art/
  palette/palette.json         swatch names → hex; the script builds the PNG
  blender/
    metic_kit.py               shared helpers (see below)
    recipes/<model>.py         one short recipe per model: build() -> root object
    build.py                   runs recipes, exports .glb, renders previews
  previews/<model>_top.png     top-down + 3/4 renders for review (committed)
               <model>_34.png
public/assets/models/<model>.glb   game-ready output (committed)
```

To compare models side by side, `python art/blender/contact_sheet.py` (Pillow)
writes `art/previews/comparison.png`: top + 3/4 views plus a thumb at true game
scale (from `art/previews/sizes.json`, written by the build).

Build (Blender 5.2, headless, from the repo root). Omit `--only` to build every
recipe; add `--no-previews` to skip renders. It prints tris/bytes/size per model
and exits non-zero if a model is over budget:

```bash
"C:/Program Files/Blender Foundation/Blender 5.2/blender.exe" -b --factory-startup -P art/blender/build.py -- --only ship_player
```

Blender cannot open scripts from very long paths (Windows MAX_PATH); keep the
repo at a short path such as `C:/Users/<you>/source/repos/Metic99`.

**Previews render with Cycles on the CPU.** Workbench/EEVEE crash in background
mode with the AMD driver on the dev machine (`atio6axx.dll` access violation).
Keep samples low (~24) → ~1 s per image.

### Kit helpers (`metic_kit.py`)

| Helper | Use |
| --- | --- |
| `hull(points, swatch, symmetric=True)` | Convex hull of points. `symmetric` mirrors across X **into one shape**: use it only for parts centered on the axis (body, canopy) |
| `pair(part_fn, ...)` | Builds a side part and a **separate mirrored copy** (wings, wingtips, engines, eyes). *The first test fused two wingtips into one slab by mirroring them as one hull; this helper prevents that.* |
| `tube(a, b, r1, r2, swatch, seg=6)` | Engines, flames, spikes, horns |
| `blob(center, r, swatch, scale)` | Low icospheres: eyes, bulbs, spots, canopies |
| `creature(nodes, edges, swatch)` | Skin-modifier skeleton (points + radii) → subdivide → decimate. Organic bodies and tentacles from ~10 points. `subdivisions=0, decimate=1` gives cheap boxy limbs |
| `lathe(profile, swatch, segments)` | Spins a `(radius, z)` side profile around Z: saucers, domes, shells, rims, pods |
| `radial(count, build_one)` | Places parts evenly around Z (tentacles, legs, rim lights, scutes) |
| `socket(name, loc)` / `anim_part(obj, role)` | Sockets and animated parts (§6) |
| `join`, `paint`, `export_glb`, `render_previews` | Plumbing |

### Variants

Recipes take a `seed` and a `palette` override so one recipe yields a family
(e.g. `alien_darter` seeds 1–5 with different horn/limb counts). Multiplayer ship
skins and "sent by opponent" aliens are palette swaps, not new models.

## 9. Agent workflow per model

1. Write/modify the recipe (~40–80 lines).
2. Run the build for that model only.
3. Review `previews/<model>_top.png` (the game view) and `_34.png`.
4. At most **2 tweak rounds**, then stop and ask the human for feedback.
5. Check budgets (build script prints tris + bytes) and commit recipe, `.glb`
   and previews together.

Rough cost: the kit is a one-time effort; afterwards ~5–10k tokens per model
including preview reviews.

## 10. Initial roster (proposal: iterate with gameplay)

Example recipes exist (2026-09-24) for `alien_darter`, `alien_lumberer`,
`alien_drifter`, and two alternative ship styles `ship_dart` (sleek delta) and
`ship_pod` (chunky round); `alien_strafer` followed (2026-09-25). **All are in
the game:** the player picks a ship on the menu, and each monster kind has its
own model and movement (AGENTS.md → Gameplay rules). More variations of both
will follow in this style.

| Model | Gameplay role | Look |
| --- | --- | --- |
| `ship_player` | The player | Fat lavender hull, cyan canopy, twin glowing engines |
| `alien_darter` | 2-number alien, fast | Small, sleek, pointed; tail/fins trailing |
| `alien_lumberer` | 3-number alien, slow | Big round body, heavy limbs, plated back |

| `ball_chip` | Number ball | Coin + digit texture (§7) |

## 11. Runtime integration

- Model names are listed in `RENDER3D.MODELS`. `BootScene` loads each
  `assets/models/<name>.glb` as a binary; `World3D.loadModels` parses them with
  `GLTFLoader` before the menu shows. Instances are clones (shared geometry and
  materials), rotated `x = +π/2` (§5).
- A missing or broken `.glb` logs a warning and the sprite-voxel model is used,
  so art lands one model at a time. Adding a model = recipe + build + add its
  name to `RENDER3D.MODELS` + use it in `World3D`.
- Done: the three ships (their `anim_flame*` parts flicker) and the four
  monsters (balls sit at `socket_balls`). `World3D` finds a monster's parts by
  name, `anim_<role>[_<side>]`, and moves them with sine motion
  (`RENDER3D.ANIM`): `tail` wags, `leg_*` swing in diagonal pairs synced to the
  lumberer's stomp, `skirt` spins and pulses, `wing_L/R` flap. Parts keep their
  Blender frame, so local Y = up (toward the camera) and local Z = tail→head;
  put a part's origin at its hinge. To do: `anim_eye` blinks, read
  `socket_muzzle` for bullets.
- The build also renders `public/assets/icons/<model>.png` (128 px, transparent,
  top-down) for 2D menus such as the ship picker.

## 12. Acceptance checklist (per model)

- [ ] Reads clearly in the top-down preview at game size.
- [ ] Main color is not a reserved ball color; ≤ 4 swatches incl. glow.
- [ ] Within triangle and file-size budgets.
- [ ] Axes/origin correct (+Y nose, +Z top, centered).
- [ ] Sockets and `anim_*` parts named per §6.
- [ ] Recipe, `.glb` and previews committed together.

## 13. Out of scope

Hand-painted/PBR textures, sculpting, skeletal rigs, AI mesh generators.
Revisit only if the low-poly style stops being enough.
